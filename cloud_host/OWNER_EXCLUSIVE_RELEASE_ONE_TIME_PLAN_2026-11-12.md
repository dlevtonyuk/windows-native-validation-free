# UAG — Owner-exclusive release authority: complete one-time setup plan
**Research record, November 12, 2026. NOT authorization to change production.**

## What has been independently verified
- Existing connected GitHub App installation reports `repository_selection=all`, so it automatically has permission to access new private repositories. **Do not create a private release repository expecting isolation until the app is narrowed to selected repositories.** The current installation lists two currently available repositories, one public development repo and one private validation repo. Both should remain explicitly selected if the owner wants to preserve the existing connected workflows. The separate future production release repository must NOT be selected.
- GitHub documentation confirms that an app can be set to **Only select repositories**, and that apps retain read-only public-repository access even when not selected. A protected production repository therefore **must be private**. https://docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps
- GitHub Free includes private repositories and **2,000 GitHub Actions minutes/month** (Linux-equivalent; Windows runners have different accounting). Required-reviewer environment rules are available for **public** repositories on Free, not private, so a private owner-only release is better governed by **a manual `workflow_dispatch` requiring an owner with write access**, and zero assistant app installation. https://github.com/pricing ; https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments
- Cloudflare's **individual Worker Editor** API token can update/deploy the one existing Worker without deletion or unrelated Worker access. This is preferable to product-wide Write or Admin. The token must be stored ONLY in the private release repository's GitHub Actions secret store; **never paste a token into ChatGPT, the public repo, screenshots or logs**. https://developers.cloudflare.com/workers/authorization/workers/
- Cloudflare Worker `windows-native-validation-free` is currently auto-deployed from the assistant-writable staging branch via `npx wrangler deploy --config wrangler.toml`; the present Cloudflare Builds token has deployment capability. Existing app/D1 controls alone cannot provide owner-exclusive control while this route exists. Official Cloudflare docs give the exact disconnect route: **Workers & Pages → target Worker → Settings → Builds → Disconnect**. Merely changing the command to `npx wrangler versions upload` reduces unintended promotion but does **not** remove privileged credentials from untrusted build scripts. https://developers.cloudflare.com/workers/ci-cd/builds/

## Owner-only trust boundary
- **Development repository**: Existing public repo, accessible to the assistant and connected GitHub App; all non-destructive R&D, synthetic CI, source-code review, and artifact simulation stay here. NO production Cloudflare deployment token in any build, workflow, repository secret, release asset, or public action log.
- **Private release repository**: Owner creates it once, keeps GitHub ChatGPT App uninstalled and existing unauthorized collaborators absent. Contains only the small, owner-reviewed release workflow, trusted bundler/configuration, and a durable owner-controlled authorization/revision ledger. Never automatically executes public-dev workflows.
- **Production release token**: New Cloudflare account-owned token, **Specified Workers → existing Worker → Editor**; stored only in private repo GitHub Actions secret. No Worker Admin, billing, DNS, broad Access or D1 permissions needed for deploying an existing Worker with an existing D1 binding (confirmed Cloudflare docs). Deployment excludes changes to routes and schedules absent separately approved/authorized scopes.
- **Owner's approval**: User signs in to GitHub and explicitly chooses a reviewed source SHA and Worker artifact hash at `Actions → owner-release → Run workflow`; owner-controlled private workflow accepts only a manually dispatched release. Separate runtime **owner capability toggles** continue to require an externally held Ed25519 private signing key, never deposited in assistant systems. Release authority and business-action authority are distinct.
- **Least-trust supply chain**: Public source is checked out at exact 40-character SHA in a secretless build job. Compiler and trusted Wrangler configuration come from the private owner repository, not the untrusted source. No npm install scripts from the public repository. A separate protected promotion job verifies the exact artifact hash and release manifest, consumes the owner approval revision, and only then accesses Cloudflare credentials. Never run public branch workflows with secrets, and never use `pull_request_target` or `workflow_run` to execute untrusted code with production tokens.
- **Trust validation**: Attempt independent read-only access checks (GitHub App installation selection and private repo visibility, Cloudflare actual scoped token role from owner confirmation), verify no secret-bearing public builds, prove unauthorized release attempts rejected, perform shadow/dry-run release, then owner-approved production cutover and rollback rehearsal.

## One complete, future owner-only intervention (DO NOT EXECUTE YET)
**Prerequisites:** independently validated and ready-to-paste trusted release workflow and shadow tests, an approved cutover/rollback plan, and a separate explicit owner decision authorizing production connection changes. Research has not met all prerequisites yet.

1. **Constrain GitHub app installation**, preserving existing access: Open **GitHub → profile → Settings → Applications → Installed GitHub Apps**. Choose **Configure** for the installed ChatGPT GitHub App. Under **Repository access**, switch **All repositories** to **Only select repositories**; explicitly select the *current two repositories* that must remain connected, including the existing public development repository and existing private validation repository. Select **Save**. If repositories differ from the last verified snapshot, review and preserve each needed existing integration; do not silently remove any.
2. **Create new private owner release repository**: From GitHub, open **New repository** (`https://github.com/new`). Choose owner account, choose a distinctive assistant-originated repository name such as `uag-owner-release-private`, choose **Private**, add README, then **Create repository**. **Do not add that repo to the ChatGPT GitHub App installation** or any other assistant-visible app. Confirm the installed app remains restricted to the previously selected development/validation repos.
3. **Provision a dedicated token**: In Cloudflare, **Manage Account → Account API Tokens → Create Token**; choose a custom permission policy for **Specified Workers**, select **windows-native-validation-free**, role **Editor**. Limit it to the correct account and avoid Billing, DNS, Workers Admin, Access and D1 write scopes. Review exact scope before creation. Copy token only once, directly into the **private repository** GitHub secret in the next step; never send it into ChatGPT.
4. **Store private credentials and trusted release workflow**: Open owner private repo → **Settings → Secrets and variables → Actions → New repository secret**, name `CLOUDFLARE_API_TOKEN` and paste the token. Store the non-secret account ID separately as an Actions variable named `CLOUDFLARE_ACCOUNT_ID`. Install the complete and independently validated owner release workflow in the private repository, using GitHub's own file editor, and restrict `workflow_dispatch` to owner-triggered releases. Avoid granting broad `contents:write` to normal build jobs.
5. **Validate before cutover**: Run a **dry-run** with no production deployment. Verify exact source commit and artifact hash, empty/isolated untrusted credentials, read-only owner release ledger state, and negative access tests. A separate fresh production release should require owner approval, with rollback manifest prepared. Confirm free-tier quota.
6. **Disconnect untrusted Cloudflare Builds AFTER private lane passes shadow validation**: In Cloudflare → **Workers & Pages → windows-native-validation-free → Settings → Builds → Disconnect**. Revoke or rotate the old automatic build token once new private release token is verified; an untrusted repo must retain **no** path to deploy code or access privileged build credentials. The existing deployed Worker should continue to serve its current version: verify unchanged Worker version, health endpoint, owner Access boundary, and D1 `jobs=0, active_policy=0` immediately after.
7. **Owner-only first release**: Approve exactly one reviewed and time-bounded source/artifact in the private repo's **Actions → owner-release → Run workflow**. Verify active Worker version, owner path protection and public API regressions; log a revision before promotion. If validation fails, stop and follow the pre-tested rollback procedure. No business adapters, Cron triggers, devices or remote Windows commands may be enabled merely because release infrastructure exists.
8. **Re-scope obsolete broad grants**: When the release lane is proven, review the ChatGPT Cloudflare OAuth's now-unnecessary `d1.write` and `access.write` permissions against ongoing approved scope, keeping read-only discovery where possible. **Do not revoke prematurely** if doing so would break still-approved setup tasks. Review any other app's repo access separately.

## Completion criteria (objective truth; not implied by configuration)
- GitHub installation `repository_selection=selected`, *owner-private release repo absent* from selected repos; assistant's actual write attempts blocked at the API authorization boundary (safely proven without modifying contents).
- Private release repository and worker token exist; release workflow protected against both assistant API edits and public CI artifact injection; no production secrets in any public repo/build.
- Cloudflare Builds production auto-deploy from assistant-writable branch disconnected and previous token revoked; current active Worker remains online.
- Each manual release maps one owner-approved commit + artifact digest to one worker version/deployment with durable, independently controlled anti-replay and rollback.
- Failed or missing audit ledger, expired signature, unknown key, altered byte, or untrusted worker scope **denies deployment**.
- Owner capability toggles retain an independent owner-exclusive signing key, requiring explicit approval for privileged business/device actions.
- Free-tier usage, recovery and rollback drills verified.
